# Plan 003：虚拟 Key 实现方案

## 分层落点

| 层 | 变更 |
|---|---|
| common | `KeyHasher`（SHA-256）、`ChatCompletionException` 新增 401/403/404 工厂 |
| api | `KeyService`、`KeyAuthDTO`、generate/info/block 请求响应 DTO |
| dal | `api_keys` 表 DDL、`ApiKeyDO`、`ApiKeyMapper`（MyBatis XML） |
| manager | `ApiKeyBO`、`ApiKeyManager`（BO↔DO、JSON 编解码） |
| service | `KeyServiceImpl`（生成、鉴权、查询、封禁） |
| core | `ChatCompletionCore` 增加模型白名单校验 |
| start | `KeyController`；`AuthFilter` 接受虚拟 key、管理面仅 master；`ChatCompletionController` 传递认证上下文 |

## 数据模型

```sql
CREATE TABLE api_keys (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  key_hash VARCHAR(64) NOT NULL UNIQUE,
  models JSONB NOT NULL,
  spend NUMERIC(18,8) NOT NULL DEFAULT 0,
  max_budget NUMERIC(18,8),
  rpm_limit INTEGER,
  tpm_limit INTEGER,
  expires_at TIMESTAMP WITH TIME ZONE,
  blocked BOOLEAN NOT NULL DEFAULT FALSE,
  metadata JSONB,
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 请求链路

```text
POST /v1/chat/completions
→ AuthFilter：master? yes → master 上下文；no → KeyService.authenticate(明文) → 查 hash/blocked/expires
→ Controller 把 KeyAuthDTO 放进 ChatCompletionReqDTO
→ Service 解析 model、取部署、构造 BO（allowedModels + masterKey）
→ Core：白名单校验（403）→ 选择部署 → 改写 → 上游 → 改写响应
```

## 关键决策

1. 白名单在 core 校验，未知模型 400 在 core 中后置判断，保证虚拟 key 越权优先返回 403。
2. 明文 key 只在生成响应出现一次；info 返回掩码。
3. 测试用 H2 PostgreSQL 模式 + `CREATE DOMAIN JSONB AS JSON`，与生产 DDL 共用。
